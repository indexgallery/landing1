# DESIGN INDEX GALLERY

Рабочий каталог мебели, искусства и света с админкой. Карточки, категории и тексты хранятся в PostgreSQL, фотографии — в объектном хранилище. Сохранение в админке сразу публикует данные без нового деплоя кода. Посетитель уже открытой страницы увидит изменения после обновления страницы.

## Рабочее развёртывание

| Что | Где |
| --- | --- |
| Сайт | https://landing1-five-omega.vercel.app |
| Админка | https://landing1-five-omega.vercel.app/admin.html |
| Репозиторий | https://github.com/indexgallery/landing1 |
| Vercel | команда `indexgallery`, проект `landing1` |
| Управление проектом | https://vercel.com/indexgallery/landing1 |
| Production-ветка | `main`; push запускает автоматический деплой |
| PostgreSQL | Neon, ресурс `landing1-db`, регион Frankfurt (`fra1`) |
| Фотографии | публичный Vercel Blob, ресурс `landing1-images`, регион `fra1` |
| API | Vercel Functions, Node.js 24, регион `fra1` |

Инфраструктура размещена в аккаунте заказчика. Первоначально перенесены 74 объекта и 80 изображений. Эти количества отражают миграцию, а не ограничения редактора.

Пароль production-админки отличается от локального. Первоначальные данные для входа сохранены на компьютере, с которого выполнялась публикация, в игнорируемом файле `backups/landing1-admin-access.txt`. В Git этого файла нет; на другом компьютере он автоматически не появится. Передайте заказчику только данные входа через согласованный закрытый канал, а не весь `.env`.

## Какие компоненты нужно поддерживать

| Компонент | Ответственность | Как обновляется |
| --- | --- | --- |
| HTML/CSS/JS сайта | страницы, карточки, фильтры, карусель | сборка и деплой Vercel из GitHub |
| Админка | редактирование объектов, категорий, текстов и фото | тот же деплой Vercel |
| Серверный API | вход, проверка данных, запись каталога, разрешение загрузки фото | тот же деплой Vercel |
| Neon PostgreSQL | опубликованный каталог, метаданные файлов, версия публикации | изменения через API; схема — отдельной миграцией |
| Vercel Blob | сами фотографии по публичным URL | загрузка через админку или первоначальный импорт |
| Docker Compose | локальные сайт/API, PostgreSQL и MinIO | только локальная разработка и тесты |

На Vercel публикуется один проект: фронтенд и API вместе. Docker-контейнеры, PostgreSQL и MinIO из Compose туда не переносятся. Neon и Blob существуют отдельно от деплоев сайта. Админка не является отдельным приложением или отдельным Vercel-проектом.

### Как проходит запрос

1. Сайт читает `GET /api/catalogue` и строит карточки из актуальных данных базы.
2. Браузер скачивает фотографии напрямую по URL Vercel Blob.
3. Администратор входит по паролю; сервер выдаёт HttpOnly-cookie на 8 часов.
4. Редактор отправляет сохранение в `PUT /api/catalogue`. Вся публикация записывается атомарно с проверкой номера версии.
5. Новое фото загружается напрямую в Blob по краткосрочному разрешению API; затем в PostgreSQL записываются его метаданные.

## Обычная работа с контентом

Откройте production-админку: можно создавать и удалять объекты, менять категории, цены, размеры, описания, порядок и фотографии, редактировать основные тексты, контакты и изображения разделов. Инструкция для редактора — [ADMIN-GUIDE.md](ADMIN-GUIDE.md).

Для изменения контента не нужны Git, Docker, npm или деплой. Локальная админка на `localhost` и production-админка работают с разными базами. Изменение локальной карточки не изменит сайт заказчика.

Если редактор сообщает о конфликте версий, чужие правки уже сохранены: скачайте резервную копию своих отклонённых правок, обновите страницу и перенесите нужные изменения в актуальную версию. Не импортируйте старую копию поверх чужих изменений без сверки.

Пока используется один общий пароль администратора. Индивидуальные аккаунты, роли и история изменений не реализованы. Удаление фотографии из карточки не удаляет сам файл из Blob: он может понадобиться для старой резервной копии. Автоматической очистки неиспользуемых файлов нет.

## Локальная разработка

Нужны Git, Docker Desktop с Compose, Node.js 22.16+ или 24 LTS; для Python-скрипта тестов — Python 3.10+. В production выбрана Node.js 24. Диапазон в `package.json` ограничен версиями ниже 25, чтобы Vercel не переключал runtime на новую неподтверждённую major-версию.

```sh
git clone git@github.com:indexgallery/landing1.git
cd landing1
npm run setup
docker compose up --build -d
```

Для текущего компьютера рабочая папка — `catalog2`, а после чистого clone она будет называться `landing1`.

Перед первым локальным импортом положите в проект папку `img/`: она намеренно не хранится в Git. Её нужно передать отдельно с исходного компьютера. `setup` создаёт `.env` со случайными паролями, не перезаписывает существующий файл и не создаёт облачные ресурсы. Зависимости npm устанавливаются внутри Docker-образа.

Первый запуск собирает MinIO из закреплённого upstream-релиза, создаёт таблицы и локальный bucket и импортирует исходный каталог. Это может занять несколько минут.

- Сайт: http://localhost:4173
- Админка: http://localhost:4173/admin.html — `ADMIN_PASSWORD` из локального `.env`.
- MinIO: http://localhost:9001 — `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` из `.env`.

```sh
docker compose ps -a
docker compose logs -f init web
docker compose down
```

Повторный запуск не перезаписывает каталог. Рабочие данные находятся в volumes `postgres-data` и `minio-data`. **`docker compose down -v` удаляет локальные данные.** Обычный `docker compose down` их сохраняет. Порты доступны только с этого компьютера. Не заменяйте локальный `DATABASE_URL` production-адресом ради тестирования.

Если Docker Desktop установлен на macOS, но `docker` не находится, включите установку CLI в настройках Docker либо для текущего терминала задайте:

```sh
export PATH="/Applications/Docker.app/Contents/Resources/bin:$PATH"
```

Если порт 4173 занят старым сервером, остановите его перед запуском Compose. При изменении локального адреса синхронно обновите `APP_ORIGIN`, S3 public URL и CORS/порты Compose.

## Проверки перед изменением кода

```sh
npm ci
npm test
npm run build
python3 scripts/test_integration.py
```

`npm test` проверяет вход, ограничения, сохранение, конфликт версий, метаданные и импорт с pg-mem и тестовым HTTP endpoint S3. Для этой команды нужен свободный локальный порт, который тест выбирает автоматически.

Python-скрипт сам создаёт отдельный Compose-проект со случайным именем, настоящими PostgreSQL и MinIO, без портов на хосте, рабочего `.env` и общих volumes. Он проверяет HTTP/API, базу, фотографии, CORS, вход/выход, поддельные cookies, Origin, валидацию и лимит входа; отдельно повторяет seed и перезапускает API, проверяя сохранность правок. При завершении, ошибке или прерывании удаляет только своё тестовое окружение. Python-зависимости устанавливаются внутри образа.

```sh
npm run test:integration
# Для медленного первого запуска:
python3 scripts/test_integration.py --startup-timeout 600
# Быстрые проверки поведения самого runner без Docker и pip:
python3 -m unittest discover -s tests/python -p test_runner.py -v
```

Для теста первого импорта также нужна локальная папка `img/`. Полный Python-прогон с Docker и проверки опубликованного API, входа и загрузки фотографий выполнены при первоначальном развёртывании. Тесты не запускаются автоматически в GitHub Actions — перед push их запускает разработчик.

## Публикация изменений кода

Основной способ — отправить проверенные изменения в `main` репозитория `indexgallery/landing1`:

```sh
git add <изменённые-файлы>
git commit -m "Describe the change"
git push origin main
```

Vercel автоматически устанавливает зависимости, собирает сайт/API и переключает production на новую сборку. Состояние смотрите в Deployments проекта `landing1`. Отдельно публиковать админку или пересоздавать базу и Blob не нужно. Изменения кода не заменяют опубликованные карточки данными из `catalog-data.js`.

Параметры сборки:

| Параметр | Значение |
| --- | --- |
| Framework Preset | Other (`framework: null`) |
| Install Command | `npm ci` |
| Build Command | `npm run build` |
| Output Directory | `public` |
| Node.js | 24.x |
| Function region | `fra1` |

Не выбирайте Container: Dockerfile нужен только локальному окружению. `.vercelignore` исключает Docker-файлы, `img/`, тесты и секреты из загрузки через CLI.

### CLI на новом компьютере

Сначала проверьте, что используется аккаунт/команда заказчика. Вход выполняйте только при необходимости; не меняйте аккаунт случайно.

```sh
npx --yes vercel whoami
npx --yes vercel teams ls
# Если вход отсутствует:
npx --yes vercel login
npx --yes vercel link --project landing1 --scope indexgallery
npx --yes vercel project inspect landing1 --scope indexgallery
```

`.vercel/project.json` — локальная привязка; в Git она не хранится. В ней должны быть проект `landing1` и команда `indexgallery`, а не старый проект `annaacme/catalog`.

При необходимости ручного релиза можно собрать production без переключения домена, проверить сборку и затем назначить её основной:

```sh
npx --yes vercel deploy --prod --skip-domain --scope indexgallery
npx --yes vercel inspect <deployment-url> --wait --scope indexgallery
npx --yes vercel promote <deployment-url> --scope indexgallery
```

Проверка входа и сохранения выполняется на основном домене после переключения: у отдельного deployment URL другой Origin. Не меняйте production `APP_ORIGIN` на временный deployment URL. Preview-веткам нужны отдельные база, хранилище и `APP_ORIGIN`; сейчас ресурсы подключены только к Production. Неработающая preview-админка без этих настроек ожидаема.

## Переменные окружения

Управление: Vercel → `landing1` → Settings → Environment Variables. Секретов в README и Git нет. Изменение переменной применяется к новым деплоям: после изменения сделайте Redeploy или новый деплой.

| Переменная | Для чего | Production |
| --- | --- | --- |
| `APP_ORIGIN` | допустимый адрес входа и изменений | `https://landing1-five-omega.vercel.app` |
| `STORAGE_DRIVER` | выбор хранилища | `blob` |
| `DATABASE_URL` | подключение API к PostgreSQL | pooled URL Neon, секрет |
| `BLOB_READ_WRITE_TOKEN` | доступ API и импорта к Blob | секрет подключённого store |
| `ADMIN_PASSWORD` | общий пароль редактора | секрет, минимум 12 символов |
| `SESSION_SECRET` | подпись сессий | случайный секрет, минимум 32 символа |

Интеграция Neon создаёт дополнительные `PG*` / `POSTGRES*` переменные. Не удаляйте их без проверки: некоторые используются инструментами интеграции. Для ручного `pg_dump` удобнее unpooled URL: `DATABASE_URL_UNPOOLED` либо `POSTGRES_URL_NON_POOLING`.

Локально при `STORAGE_DRIVER=s3` нужны `S3_ENDPOINT`, `S3_PUBLIC_ENDPOINT`, `S3_PUBLIC_URL`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_FORCE_PATH_STYLE`; шаблон — [.env.example](.env.example). В текущем production они не нужны.

Для обслуживания можно получить production-конфигурацию в игнорируемый файл:

```sh
npx --yes vercel env pull .env.vercel.local --environment production --yes --scope indexgallery
chmod 600 .env.vercel.local
```

Этот файл содержит доступ к базе, файлам и админке. Не коммитьте его, не отправляйте в чат и не передавайте целиком заказчику. Для входа редактора достаточно отдельно передать URL админки и пароль.

### Смена пароля и домена

- Чтобы сменить пароль, обновите `ADMIN_PASSWORD` в Production и выполните Redeploy. Старые сессии перестанут проходить проверку новым кодом/окружением; пользователи войдут новым паролем. Обновите собственную закрытую запись с данными доступа.
- Ротация `SESSION_SECRET` также делает старые сессии недействительными после деплоя. Не меняйте его при каждом обычном обновлении кода.
- Для нового домена сначала подключите и подтвердите его в Vercel → Domains, затем задайте в `APP_ORIGIN` точный `https://домен` без пути и выполните Redeploy. Админку открывайте на этом основном адресе. Альтернативный alias с другим Origin может отклонять сохранение.

## Схема и первоначальный импорт

Таблицы:

- `catalog_state`: единственная строка `id=1`; `payload` содержит `products`, `categories`, `site`; `revision` защищает от перезаписи устаревшей вкладкой.
- `media`: ключ объекта, публичный URL, MIME-тип, размер и дата создания файла.
- `login_attempts`: счётчики неудачных входов с временным окном 15 минут.

При обычном деплое миграции и seed автоматически не выполняются. `scripts/migrate.mjs` сейчас содержит идемпотентное создание таблиц через `CREATE TABLE IF NOT EXISTS`; полноценной системы последовательных миграций и автоматического отката схемы пока нет.

Перед изменением схемы сделайте резервную копию, проверьте SQL на отдельной базе и обеспечьте совместимость со старой работающей версией API. Затем примените миграцию к нужной базе и публикуйте код:

```sh
node --env-file=.env.vercel.local scripts/migrate.mjs
```

`seed` нужен только для пустой базы. Если `catalog_state` уже существует, он пропускает импорт и сохраняет правки редактора:

```sh
node --env-file=.env.vercel.local scripts/seed.mjs
```

По умолчанию импорт берёт `catalog-data.js`, `site-data.js`, локальные фото `img/` и фотографии разделов из HTML. Для импорта сохранённого снимка в пустую базу можно явно указать файл:

```sh
CATALOG_IMPORT_FILE=backups/import.json node --env-file=.env.vercel.local scripts/seed.mjs
```

Снимок должен содержать `products`, `categories`, `site`. Фото по локальным путям и data URI отправляются в выбранное хранилище. **HTTP(S)-ссылки seed оставляет как есть**, он не переносит файлы из другого S3 автоматически. До импорта снимка с `localhost:9000` нужно скачать фото, заменить ссылки локальными путями, а затем импортировать в облако. Резервная копия той же production-базы уже ссылается на рабочий Blob.

Не запускайте `scripts/build_catalog_data.py` как способ обновить production: это старый генератор из Excel. После миграции единственный источник актуальных карточек — база, а не Excel или JS в Git.

### Если нужно создать другое окружение с нуля

Создайте/выберите Vercel-проект в нужном аккаунте, подключите GitHub и Production-ресурсы Neon и Blob, задайте переменные из таблицы, примените схему и импортируйте данные. Условия сервисов принимает владелец аккаунта. Затем выполните деплой.

Для этих шагов есть вспомогательный скрипт:

```sh
npm run vercel:setup -- --origin https://NEW-PROJECT.vercel.app --scope NEW-TEAM
```

Это не команда обычного обновления существующего сайта: она может создать реальные ресурсы. Сначала проверьте привязку проекта и список ресурсов. При неудаче provisioning скрипт сохраняет отметку в `.vercel/catalog-setup.json`; проверьте уже созданный ресурс и подключите его, вместо повторного создания. Для импорта вне Vercel нужен `BLOB_READ_WRITE_TOKEN`. Секреты скрипт получает в `.env.vercel.local`; целиком файл не передаётся.

## Резервные копии

Нужны две независимые части: **данные PostgreSQL и файлы Blob**. Репозиторий Git не является резервной копией опубликованного каталога. JSON и ZIP из админки содержат ссылки на фото, а не сами файлы.

Перед массовым импортом, удалением карточек, изменением схемы или очисткой хранилища:

1. Скачайте JSON кнопкой «Резервная копия» в админке.
2. Сохраните полный дамп PostgreSQL через `pg_dump` или поддерживаемый инструмент Neon. Используйте клиента PostgreSQL, совместимого с версией сервера, и храните дамп вне рабочего компьютера и Git.
3. Скопируйте файлы Blob в отдельное хранилище вместе с соответствием исходных URL и имён. При восстановлении в другой Blob store URL изменятся — ссылки в каталоге тоже нужно будет заменить.
4. Проверьте восстановление на отдельной базе/хранилище, прежде чем считать копию рабочей.

Плановые автоматические резервные копии и регулярная выгрузка Blob в проекте не настроены. Возможность и срок восстановления Neon зависят от настроек/тарифа провайдера; заранее проверьте их в панели базы. Назначьте ответственного за копии и их проверку.

Для локальной базы можно сделать дамп так:

```sh
mkdir -p backups
docker compose exec -T postgres pg_dump -U catalog -d catalog -Fc > backups/catalog-local.dump
```

Команда перезаписывает файл с тем же именем; для нескольких копий используйте разные имена. Локальные фото находятся отдельно в MinIO volume `minio-data` — дамп PostgreSQL их не включает.

### Восстановление

- Для возврата карточек/текстов при сохранных фото импортируйте проверенный JSON через админку. Импорт заменяет опубликованный каталог и сразу становится видим посетителям.
- Для полного восстановления сначала поднимите новую пустую PostgreSQL-базу, восстановите дамп через `pg_restore`, проверьте фотографии и доступ, затем переключите `DATABASE_URL` и сделайте Redeploy. Не применяйте разрушительное восстановление к рабочей базе без проверенной копии.
- Если потеряны или перенесены фото, восстановите файлы, обновите URL в снимке каталога и метаданные `media`, проверьте карточки и только затем переключайте production.

`backups/`, `img/`, `.env*` и `.vercel/` игнорируются Git. На чистом clone их нет: первичные картинки, доступы и резервные копии передаются отдельно. Production-сборке после заполнения базы и Blob папка `img/` не нужна.

## Диагностика и откат

Быстрая проверка API:

```sh
curl --fail https://landing1-five-omega.vercel.app/api/health
curl --fail https://landing1-five-omega.vercel.app/api/catalogue
```

`/api/health` проверяет доступность PostgreSQL. `/api/catalogue` должен вернуть JSON с карточками и версией; это не подтверждает доступность всех фотографий или загрузку новых файлов — их проверяйте отдельно.

```sh
npx --yes vercel ls landing1 --scope indexgallery
npx --yes vercel inspect <deployment-url> --scope indexgallery
npx --yes vercel logs --project landing1 --environment production --query 'level:error' --since 1h --scope indexgallery
```

| Симптом | Что проверить |
| --- | --- |
| Сайт пустой / API 503 | runtime-логи, `DATABASE_URL`, доступность Neon, выполненные migrate/seed |
| Фото не видно | URL и HTTP-ответ файла, наличие его в нужном store; нет ли локального `localhost` в production-данных |
| Новое фото не загружается | production `STORAGE_DRIVER=blob`, токен нужного store, ответ `/api/blob-upload`, JPG/PNG/WebP до 8 МБ |
| «Недопустимый источник запроса» | основной адрес админки совпадает с `APP_ORIGIN`; после смены адреса был Redeploy |
| Неверный пароль / 401 | production-пароль, а не локальный; истекла ли 8-часовая сессия |
| Слишком много попыток / 429 | подождать 15 минут перед повторным входом |
| Конфликт версии / 409 | другой редактор уже сохранил данные; сверить правки с актуальной версией |
| Vercel собирает контейнер | Framework Other, `framework: null`, настройки `vercel.json` |
| Сборка упала после push | Deployments → Build Logs, lockfile, Node.js и команда сборки |

Для отката неудачного релиза используйте предыдущий успешный production deployment в панели Vercel либо:

```sh
npx --yes vercel rollback <previous-deployment-url> --scope indexgallery
```

**Откат деплоя откатывает код, но не PostgreSQL, не изменения карточек и не файлы Blob.** Если менялась схема базы, сначала проверьте совместимость старого кода. После rollback проверьте в Vercel автоматическое назначение следующих production-деплоев; при необходимости используйте Promote для выбранной проверенной сборки.

## Передача и регулярное сопровождение

Заказчик должен владеть GitHub, командой Vercel, Neon, Blob и доменом. Разработчику предоставляются отдельные приглашения, а не общий пароль владельца. Для повседневной работы заказчику нужны только адрес админки и пароль редактора.

При передаче проверьте доступ владельца ко всем сервисам, передайте закрытые данные входа и инструкцию редактора, назначьте ответственного за резервные копии и оплату/лимиты сервисов. Не удаляйте аккаунт, интеграцию или Blob store до проверки зависимостей и копий.

При сопровождении после релиза проверяйте каталог, открытие карточки, фотографии, вход и сохранение в админке, runtime-логи и лимиты базы/хранилища. Обновления зависимостей сначала проверяйте локально тестами, затем публикуйте отдельным изменением. Расширения редактора, права сотрудников и автоматические копии требуют отдельной реализации.
